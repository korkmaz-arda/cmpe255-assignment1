# Market Basket Intelligence & Associative Pattern Mining

Association-rule mining over **real Instacart grocery orders**. Three frequent-itemset algorithms
(Apriori, FP-Growth, ECLAT) are implemented from scratch and benchmarked against each other and
against a maintained reference library; the resulting rules drive a live cross-sell recommender, a
product-affinity network, a searchable rules explorer and an autonomous four-phase parameter search —
all behind a two-view Streamlit dashboard.

> **Reproduction note.** This is an independent reimplementation from a written specification of an
> existing project. Where that specification documented defects — a prefix-tree miner that did not
> mine, a synthesised runtime used to award a "champion" badge, graph edges asserting affinities no
> rule states, sliders wired to nothing, and a hardcoded "SOTA" constant with no provenance — this
> implementation does the intended thing instead and says so. See
> [Deviations from the source specification](#deviations-from-the-source-specification).

## Quick start

```bash
conda activate cmpe255
pip install -r requirements.txt

python -m basket.data --download     # fetch Instacart, build catalog + corpus  (207 MB download)
python -m basket.pipeline            # mine the rule set, write artifacts       (~8s)
python -m basket.autoresearch        # run the four-phase parameter search      (~10s)

pytest -q                            # 89 tests, fully offline, ~4s
streamlit run app/main.py            # open the dashboard
```

A committed `.streamlit/config.toml` disables usage telemetry and runs the server headless, so the
first launch on a clean machine never stops to ask for an email address. Because headless mode does
not open a browser tab, open the printed `Local URL` yourself.

The dashboard can also re-mine and re-run the search on demand, so the two middle commands are
optional once the data is downloaded — but running them first gives you a populated dashboard on the
first load.

## The data

| | |
|---|---|
| **Source** | [Instacart Online Grocery Basket Analysis](https://www.kaggle.com/datasets/psparks/instacart-market-basket-analysis) — public, no credentials, no competition sign-up |
| **Used** | `order_products__train.csv` (1,384,617 rows / **131,209 real orders**), plus `products`, `aisles`, `departments` |
| **Not used** | the 32 M-row `prior` split and `orders.csv` — neither is needed for basket mining |
| **Location** | `data/raw/` and `data/processed/`, both gitignored and regenerated by script |

Nothing is committed: `python -m basket.data --download` fetches and prepares everything. If the
endpoint ever changes, the script fails with manual-download instructions rather than proceeding
silently.

### The canonical item is `product_id`

Itemsets, rules, tidsets, graph nodes, recommendations and the search trajectory are all keyed on the
Instacart `product_id`. Product names, aisles, departments and colours are display metadata joined at
the presentation edge. Names are not unique and are never used as keys.

### Catalog: a frequency floor, not a top-N

A product enters the mining catalog when it appears in **at least 0.5% of orders**, measured over the
*full* train split before any sampling — so the catalog is a property of the dataset, not of whatever
orders were drawn. That admits **256 products**.

The floor is five times the production support threshold. An itemset can never be more frequent than
its rarest member, so a product below that line has no headroom to take part in a frequent pair. It
is a frequency rule, applied blind to what the products are, and it is not tuned to produce better
rules.

### The support denominator includes sparse baskets

Orders are projected onto the catalog, and an order left with **fewer than two** catalog products is
**kept in the corpus**. It cannot contribute a candidate combination, but it is a real order that did
not contain the pairs being scored — negative evidence. Of the 131,209 orders mined, 82,203 can
contribute a candidate, and all 131,209 sit in the denominator of every support figure.

Dropping the sparse ones would shrink that denominator, inflating every support and distorting every
metric derived from it. A test pins the denominator to the sampled order count.

### Prices are synthetic and stay out of the science

Instacart publishes no prices. The app generates one per product from a fixed seed so the basket
panel has something to add up. They are labelled *illustrative* everywhere they appear, and they are
**not** written into the graph artifact, never read by mining, rule scoring or recommendation
ranking. A test changes the price seed and asserts the itemsets, rules, graph artifact and
recommendation ordering come out identical.

Monetary figures in the UI are therefore described as *illustrative potential add-on value*, never as
measured or projected revenue uplift.

## Thresholds, and why these numbers

Real grocery baskets at product granularity are far sparser than a small synthetic catalog. The most
common product (Banana) appears in ~14% of orders; most appear in well under 1%. Pair frequencies are
correspondingly small, so the support floors here are around 0.1%, an order of magnitude below the
specification's synthetic-corpus values.

They are set by **evidence count**, not by the rule counts they produce:

| Pass | min support | ≈ orders behind an itemset | max length | min confidence | min lift |
|---|---:|---:|---:|---:|---:|
| Benchmark | 0.0015 | ~197 | 4 | 0.20 | 1.20 |
| **Production** *(served)* | 0.0010 | ~131 | 4 | 0.25 | 1.25 |
| Search baseline | 0.0015 | ~197 | 4 | 0.20 | 1.20 |
| Search trials | 0.0003 – 0.0020 | ~39 – 262 | 2, 4 or 5 | 0.20 – 0.40 | 1.00 – 2.20 |
| Re-mining UI | 0.0005 – 0.0100 | — | 4 | 0.10 – 0.90 | 1.0 – 5.0 |

The benchmark pass uses the higher support with looser rule gates, the production pass the lower
support with stricter ones — the same structure as the specification's table, with the numbers taken
from this corpus.

## Results

Every number below was produced by this pipeline and can be regenerated with
`python -m basket.pipeline`. They are measurements, not targets.

### Production rule set

| | |
|---|---:|
| Orders mined | 131,209 |
| Catalog products | 256 |
| Frequent itemsets | 2,723 |
| Active rules | 600 |
| …of which single-product ➔ single-product | 126 |
| Top lift | 46.96x *(191 orders)* |
| Mean lift | 4.06x |
| Mean confidence | 32.4% |
| **Basket coverage** | **61.4%** of real baskets fire at least one rule |

Basket coverage is reported because a rule count alone can hide a rule set that never fires. The
remaining 38.6% of baskets genuinely have no recommendation, and the UI says so rather than showing
an empty panel.

A sample of what the mining finds — all of it real structure in real orders:

| Rule | Lift | Confidence | Support | Orders behind it |
|---|---:|---:|---:|---:|
| Icelandic Skyr Blueberry Yogurt ➔ Vanilla Skyr Nonfat Yogurt | 46.96x | 27% | 0.146% | 191 |
| Sparkling Lemon Water + Grapefruit ➔ Lime Sparkling Water | 30.02x | 45% | 0.113% | 148 |
| Yellow Bell Pepper ➔ Orange Bell Pepper | 23.91x | 34% | 0.302% | 396 |
| Organic Red Onion + Limes ➔ Organic Cilantro | 11.78x | 32% | 0.159% | 209 |
| Organic Yellow Onion + Italian Parsley ➔ Organic Garlic | 11.17x | 35% | 0.101% | 132 |

**Read lift together with the evidence behind it.** The highest-lift rules tend to be the rarest:
the 46.96x rule rests on 191 of 131,209 orders. Lift says those two yogurts are bought together
far more often than chance — a genuine association — but a rare combination with a huge lift is not
automatically strong business evidence, and none of these numbers say that one purchase *causes*
another. The dashboard shows support and the order count beside every high-lift figure for this
reason.

### Algorithm benchmark

All four entrants mined the **same** 131,209-order corpus at the **same** thresholds (support ≥
0.0015, itemsets up to 4 products, confidence ≥ 0.20, lift ≥ 1.20). Every runtime is the measured
wall-clock time of the run that produced its own row — nothing is scaled, floored or synthesised.

| | Algorithm | Role | Itemsets | Rules | Top lift | Mean confidence | Runtime |
|---|---|---|---:|---:|---:|---:|---:|
| 🏆 | **ECLAT** | implemented here | 1,469 | 487 | 25.59x | 27.5% | **0.531s** |
| | Apriori | implemented here | 1,469 | 487 | 25.59x | 27.5% | 0.704s |
| | FP-Growth | implemented here | 1,469 | 487 | 25.59x | 27.5% | 0.857s |
| 🔍 | mlxtend `apriori` + `association_rules` | **external reference** | 1,469 | 487 | 25.59x | 27.5% | 3.452s |

All four agree exactly on the itemsets and their supports, which is the invariant the comparison
rests on — these are exact algorithms, so they can only differ in cost.

**About the reference row.** `mlxtend` is a maintained third-party library run on the same corpus at
the same thresholds. It is here to independently confirm the results are right. It is not a fourth
algorithm family, not a state-of-the-art claim, and it is excluded from the runtime ranking and the
champion badge — its runtime reflects a different engineering approach (a one-hot pandas matrix), not
a different mining paradigm.

**On the champion.** ECLAT is fastest here on honest measurement. Bitwise intersection of integer
tidsets is simply cheaper in pure Python than building and walking a tree. The source specification
described an FP-Growth backbone badged as champion on a runtime multiplied by a constant; measured
properly, the ordering is the other way round.

### Parameter search

Four phases, 11 trials, on the same corpus as production so the mean-lift figures are directly
comparable. Objective: mean lift across the surviving rule set.

| | |
|---|---:|
| Mean lift | 3.434 → **5.384** (+56.8%) |
| Trials | 11 (3 accepted, 7 rejected) |
| Best configuration | support 0.0003, max length 5, confidence 0.40, lift 1.60 |
| Applied to production? | **No** — reported, not applied |

**Acceptance rule:** a trial is adopted only when it improves mean lift by more than 0.02 **and**
leaves at least 10 rules standing (8 in phases 3–4). The rule floor is deliberate and applies to
every trial in its phase: mean lift on its own is trivially inflated by tightening thresholds until a
handful of freak rules remain, which would be useless to the recommender. It is a rule-set quality
heuristic, not a generalization estimate — there is no held-out evaluation here, and none would be
meaningful for counted facts about a corpus.

Phase 4 raises the itemset cap to 5, because a 4-product antecedent requires a 5-item itemset, and
drops the support floor to 0.0003 (~39 orders) so such a combination can clear it at all. That is
thin evidence per rule, and the trajectory says so in its own reflection rather than glossing over
it.

The rejected trials are kept and displayed. The dead ends are how the final configuration was
reached.

**The search is exploratory; it does not change what the app serves.** Its best configuration buys
a higher mean lift (5.38 vs the production set's 4.06) with roughly a third of the evidence per rule
(~39 orders vs ~131). That trade is shown, not made for you: the production rule set stays at the
conservative threshold, and the dashboard says so wherever the search's figures appear.

## Architecture

```
basket/          analytical core — plain Python, no UI framework import anywhere
  config.py      paths, dataset coordinates, thresholds, validation ranges, seeds
  data.py        acquisition, catalog, corpus            (CLI: -m basket.data --download)
  mining.py      apriori / fpgrowth / eclat, each measured
  rules.py       partitions and the five metrics
  graph.py       product-affinity network
  recommend.py   basket → ranked cross-sell
  reference.py   mlxtend reference run + agreement check
  benchmark.py   leaderboard assembly
  autoresearch.py four-phase search                       (CLI: -m basket.autoresearch)
  pipeline.py    benchmark + production passes, artifacts (CLI: -m basket.pipeline)
  engine.py      artifact loader + version stamp
app/             Streamlit + Plotly
  main.py        navigation, status badge, glossary sidebar
  state.py       the only Streamlit caching in the project
  workspace.py   basket, recommendations, affinity network, metric strip
  admin.py       benchmark / search / rules explorer / re-mine
  crispdm.py     six-phase report, driven by live artifacts
  glossary.py    plain-language definitions and tooltips
tests/           offline, fixture-backed
artifacts/       gitignored, regenerated by the pipeline
data/            gitignored, regenerated by the download script
```

**Artifact-backed serving.** The app never mines at request time. The pipeline writes `rules.json`,
`graph.json`, `benchmarks.json`, `catalog.json`, `run_meta.json` and `autoresearch.json`; the engine
loads them once and answers from memory, which is why a suggestion takes ~0.1 ms. Re-mining rewrites
those files, the version stamp changes, and every session picks up the new rule set without a
restart.

**Core/UI separation.** `basket/` has no Streamlit or Plotly import. A test imports the entire package
with both blocked, so the analytical core stays usable and testable with no UI framework installed.

## Tests

```bash
pytest -q        # 89 tests, offline, ~4s
```

Everything runs against a small committed fixture in the real Instacart schema — 105 orders over 11
products, built so each property under test is hand-checkable, including a block of orders that
project to empty baskets and a genuine 5-itemset. Every path the package writes to is redirected into
`tmp_path`. Nothing downloads.

The tests that matter most:

* the three implementations find **identical** itemsets and supports, and agree with mlxtend;
* FP-Growth genuinely mines through conditional pattern bases, rather than delegating;
* ECLAT applies the support threshold at emission, not only before recursion;
* metrics match hand computation, confidence is asymmetric, conviction stays finite at confidence 1;
* sparse and empty baskets remain in the support denominator;
* every graph edge comes from a rule with a single product on each side;
* changing the price seed moves no itemset, rule, graph or ranking;
* the recommendation badge comes from the rule that produced the ranking score;
* each of the four re-mining controls independently changes the result;
* the search's gain threshold and rule floor both reject, in both directions;
* Phase 4 mines at length ≥ 5 and reaches a 4-product antecedent;
* the rendered app, not just the core: the graph tooltip shows department, frequency and the
  illustrative price; selecting a product dims its non-neighbours; a stale selection is dropped;
  an empty rule set shows "—" rather than a fabricated "0.00x"; each re-mine slider reaches the
  pipeline; and the outcome of a re-mine is still on screen after the app reloads.

## Deviations from the source specification

Two are user-approved adaptations of a requirement; the rest are corrections of defects the
specification itself documented.

| # | Source behaviour | What this implementation does | Why |
|---|---|---|---|
| 1 | `F01` generates a synthetic 33-product corpus from five authored archetypes | Mines **real Instacart orders** | User decision. The source documented Instacart throughout while generating its own data; every lift in it was an artifact of the generator. |
| 2 | `F07` shows a hardcoded "Kaggle Grandmaster SOTA" row (284 itemsets, 4.85 lift, 3.82 s) | Runs **mlxtend** on the same corpus and thresholds and labels it an **external reference**, excluded from the ranking and the badge | User decision. The constant had no provenance and was never computed. A real library run on the same data is both honest and useful. |
| 3 | The prefix-tree miner builds a tree, discards it, and returns Apriori's itemsets | **FP-Growth is really implemented** — header table, conditional pattern bases, recursive conditional trees | A named algorithm's output should come from that algorithm. |
| 4 | FP-Growth's runtime is the tree-build time × ~0.45, then used to award the champion badge | **Every runtime is measured**, around only that algorithm's own work | A benchmark timing must reflect the work actually done. Measured honestly, ECLAT wins. |
| 5 | Each rule draws one edge between its *first* antecedent item and its *first* consequent item | The network draws **only single-product ➔ single-product rules** | `{A,B} ➔ C` asserts nothing about A and C alone. Decomposing multi-item rules into pairwise edges has the same flaw, so neither is done. Multi-item rules keep their full meaning in the recommender and the rules table. |
| 6 | Three of the four re-mining sliders are transmitted but ignored | **All four controls change the result** | A control that does nothing misrepresents the result the user is shown. |
| 7 | A candidate's displayed lift and confidence are independent maxima; the named rule is whichever fired first | The badge shows the lift and confidence of **the rule that produced the ranking score** | Otherwise the number, the named rule and the ordering can all disagree. |
| 8 | The trajectory chart uses a hardcoded y-range; committed trials fall off-chart | The range **follows the data** | A chart that hides its own data points is worse than no chart. |
| 9 | Headline figures (SOTA lift, evolved lift, latency) are static display text | All three are **computed** from the current artifacts and a live measurement | Displayed numbers should trace to a computation. |
| 10 | The CRISP-DM report is authored prose, fixed at write time | The report reads **live numbers from the current run's artifacts** | So it cannot drift away from the pipeline. |
| 11 | Documentation claims Instacart, "500+ SKUs", cross-validation, leakage audits, force-directed layout | This README and the UI describe **what exists**: real Instacart data, 256 catalog products, no cross-validation (none is meaningful), a precomputed circular layout | — |

### Honest limitations

* **Basket coverage is 61.4%.** Real baskets are diverse; the rest fire no rule. This is reported in
  the UI rather than hidden.
* **Rules concentrate in a few aisles** — fresh produce, sparkling water, yogurt. That is where the
  co-occurrence structure genuinely is.
* **The search's best configuration mines at ~39 orders per itemset.** It wins on mean lift, but the
  evidence behind each individual rule is thin, and the trajectory says so. The production rule set
  deliberately stays at the more conservative ~131-order floor.
* **Prices are invented.** Every monetary figure is illustrative, and labelled as such.
