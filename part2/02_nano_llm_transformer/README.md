# NanoLlama — a tiny character-level transformer, trained from scratch

NanoLlama is a ~4.8M-parameter decoder-only language model built from explicit
primitives (RoPE, SwiGLU, RMSNorm, causal attention with a KV cache, tied embeddings).
It is trained on this machine with assistant-only loss and served in a five-tab web studio:
**Chat**, **Attention**, **Tokenizer**, **Telemetry** and **Architecture**, plus an in-app
**Retrain** dialog.

Every chat reply is generated autoregressively by the model, one character at a time.
There is no retrieval, prompt matching, canned answer or hidden fallback text.

> **"SFT" in this project** means *supervised instruction training from random
> initialization*: next-character prediction where the loss is computed only on
> assistant replies (and the EOS that ends each reply). There is **no pretrained base
> model**; this is not fine-tuning of an existing LLM.

## Quick start

```bash
conda activate cmpe255

# 1. Dependencies (PyTorch CUDA 13.0 wheel supports RTX 50-series / Blackwell sm_120)
pip install torch==2.14.0 --index-url https://download.pytorch.org/whl/cu130
pip install -r requirements.txt

# 2. Data: downloads ~2.7 GB (TinyStoriesInstruct) + 2 MB (Everyday Conversations) into data/raw,
#    then builds the windowed train/val/test splits in data/processed (a few minutes after download)
python scripts/prepare_data.py

# 3. Tests (offline, CPU, about 1-2 min; they never need the downloaded data)
python -m pytest

# 4a. Short validation run (~1 min on the RTX 5090)
python scripts/train.py --preset smoke
# 4b. Full training run (~23 min on the RTX 5090; logs in artifacts/logs/)
python scripts/train.py

# 5. Final held-out evaluation of the promoted version — run ONCE, after choosing the production model
python scripts/finalize.py

# 6. Web app (localhost only)
uvicorn app.server:app --host 127.0.0.1 --port 8000
# open http://127.0.0.1:8000
```

A CPU-only machine works too (`pip install torch==2.14.0`). Training is much slower there;
use `--max-story-windows` to shrink it.

## Data

| Source | What it is | Licence | How it is used |
|---|---|---|---|
| [`roneneldan/TinyStoriesInstruct`](https://huggingface.co/datasets/roneneldan/TinyStoriesInstruct) | **Public synthetic dataset**: short children's stories generated by GPT-3.5/GPT-4, each with constraint fields (Words, Features, Summary, Random sentence) | CDLA-Sharing-1.0 | Instruction → story dialogues under the storyteller persona |
| [`HuggingFaceTB/everyday-conversations-llama3.1-2k`](https://huggingface.co/datasets/HuggingFaceTB/everyday-conversations-llama3.1-2k) | **Public synthetic dataset**: 2–4-exchange small-talk conversations generated by Llama-3.1-70B-Instruct | Apache-2.0 | Multi-turn chats under the default assistant persona |
| Project knowledge base (`nanollama/kb.py`) | 48 hand-written Q&A entries (identity/architecture, ML basics, metrics, algorithms, Python, math, stories, small talk), each with 4 paraphrases and in-scope personas | this project | Persona dialogues (six personas) |

Neither external dataset is human conversation data; both were generated by larger
language models.

### Splits (made at source level, before any windowing)

| Source | Train | Validation (checkpoint selection) | Final held-out test (`finalize.py` only) |
|---|---|---|---|
| TinyStories | seeded, content-blind sample of **60,000** of 2,476,533 records in the train file (6 unparseable records skipped) | 1,000 records from the official valid file | 2,000 other records from the official valid file |
| Everyday | official train minus a seeded 5% (2,112 after dedup) | that 5% (112) | official test split (119) |
| KB | 32 entries, one paraphrase each withheld | 8 entries (1 per topic, seeded) | 8 entries (1 per topic, seeded) |
| KB rephrasing diagnostic | — | — | the withheld paraphrases of the 32 train entries: **answer seen during training; wording held out** |

- **Validation and test rows are fixed** and do not depend on the TinyStories training sample size.
- **Dedup / leakage control:** normalized (case, punctuation, whitespace) hashes.
  - TinyStories train stories matching val/test stories are removed (0 found).
  - Everyday train conversations are removed if they match a val/test conversation or share any normalized assistant turn of ≥ 40 characters (35 removed; 1 val conversation removed for matching test).
  - KB train queries or answers equal to held-out ones are removed.
  - Dialogue ids are asserted never to appear in two splits.
- Everyday conversations ending in a user message with no reply keep all their turns except that trailing message (255 train, 13 test); nothing is discarded.
- Text is normalized to the ASCII vocabulary (smart quotes and dashes mapped, NFKD fold). Remaining unknown characters become a space; the replacement rate is 5.6e-8 for TinyStories train and 6.0e-5 for Everyday train.

### Context windows (1,024 characters)

Examples are never silently truncated.
- An example that fits is one unchanged window.
- **Conversations** that do not fit are split along turn boundaries. Every window reopens with BOS + system prompt and starts at a user turn.
- **Long stories** (or one over-long reply) are chunked. Every chunk keeps the full conditioning prefix (BOS, system prompt, user instruction, assistant marker), then a masked overlap from the previous chunk, then fresh target characters. Each reply character is supervised **exactly once** (tested).
- Examples whose prefix leaves no room are counted as dropped (none in the current data).

| Train split | Examples | Fit directly | Windowed | Windows | Dropped |
|---|---|---|---|---|---|
| TinyStories | 59,994 | 20,326 | 39,668 | 111,506 | 0 |
| Everyday | 2,112 | 2,010 | 102 | 2,214 | 0 |
| KB | 285 dialogues | 285 | 0 | 285 | 0 |

Full per-split counts are in `data/processed/manifest.json` and in each version's `data_report.json`.

## Model (`nanollama/model.py`)

| | |
|---|---|
| Vocabulary | 104 fixed tokens: `<\|pad\|> <\|bos\|> <\|eos\|> <\|user\|> <\|assistant\|> <\|system\|>` (ids 0–5), then printable ASCII, `\n`, `\t`, `\r` |
| Layers / width / heads | 6 / 256 / 8 (head dim 32) |
| Feed-forward | SwiGLU, hidden width 688, bias-free |
| Normalization | RMSNorm (float32) before attention, before the feed-forward block, and before the head |
| Positions | Rotary embeddings on Q and K, interleaved pairs, base 10000, absolute-position slicing when cached |
| Attention | Fused `scaled_dot_product_attention` for full passes; explicit score/mask/softmax path for the KV cache and attention maps (tested equal) |
| Head | Tied to the token embedding |
| Parameters | **4,773,120** (closed-form count tested) |
| Context | 1,024 characters |

Chat template: `BOS <|system|>S <|user|>U1 <|assistant|>A1 EOS <|user|>U2 <|assistant|>…`.
Message bodies are encoded as plain characters, so a literal `<|user|>` typed in a message cannot forge a role boundary.

## Training (`nanollama/train.py`)

- **Objective:** masked next-character cross-entropy on assistant reply characters and their EOS.
- **Optimizer:** AdamW (β 0.9/0.95, weight decay 0.01 on matrices and embeddings), gradient clipping 1.0, peak LR 2e-3, 5% linear warmup, then cosine decay to 5% of peak.
- **Defaults:** 8 epochs, batch 32, seed 1234, bf16 autocast, `torch.compile` on CUDA.
- **Mixture per epoch:** TinyStories ×1, Everyday ×1, KB ×8 (97.2% / 2.0% / 0.8% of target characters). Repeats apply to the training split only.
- **Checkpoint selection:**
  ```
  selection_loss = (tinystories_val_loss + everyday_val_loss) / 2
  ```
  - The epoch with the lowest selection loss is saved. A later epoch replaces it only if it is lower by more than 0.001 nats (effective ties keep the earlier epoch).
  - **KB validation loss is computed every epoch and shown as a diagnostic, but is not used for selection.** KB validation entries contain answers never seen in training, so their loss rises as the model memorizes the training KB. In an earlier run that equally weighted all three sources (with Everyday ×7 and KB ×45 per epoch), KB-val rose every epoch (2.76 → 6.18). That rule selected epoch 1 and discarded seven epochs of TinyStories improvement. The heavy repeats also overfit Everyday-val after epoch 2. Both were changed; these decisions used validation data only.
- **Test sets are never read during training or retraining.** Training code can only open `train`/`val` files; a test asserts this.

### Versioned artifacts

Each run writes `artifacts/versions/<run-id>/`:
- `checkpoint.pt`, `config.json`, `vocab.json`
- `telemetry.json`: curves, optimizer, environment, measured throughput
- `validation.json`: selected-epoch validation, unigram baseline, samples
- `data_report.json`, `promotion.json` (written at the version's first promotion and never rewritten; every promotion attempt, including re-promoting an older version, is appended to `artifacts/promotion_history.jsonl`)

Promotion runs in this order:
1. Verify the files.
2. Rebuild the model from `config.json`.
3. Probe with a forward pass plus a short generation (logits must be finite).
4. Atomically replace **only** `artifacts/current.json`.

On any failure the previously served version stays active. `final_eval.json` is added to a version directory only by `scripts/finalize.py`.

### Finalization (`scripts/finalize.py`)

- Scores the version in `current.json` on the four held-out sets: masked loss/perplexity, the unigram baseline, and greedy samples. For KB sets it adds a character similarity ratio to the reference (difflib; character overlap, not semantic correctness; descriptive only).
- Refuses if the prepared data no longer matches what the version was trained on.
- Refuses a second run on the same version unless `--force` is given; forced reruns are appended to `finalize_history`.
- A newly trained or retrained version always starts **not finalized**.

## Measured results (version `20260916-181935-run`)

Environment: RTX 5090 Laptop GPU, torch 2.14.0+cu130 (arch list includes `sm_120`), Python 3.11.

- Wall clock 23.1 min for 8 epochs; mean **591k training tokens/s**; 810M input tokens processed.
- Saved epoch **7** (selection loss 0.6486; epoch 8 was 0.6481, within the tie tolerance).

**Validation (used for checkpoint selection, so not an unbiased estimate):**

| Validation source | Loss (nats/char) | Perplexity | Unigram baseline loss | Characters scored |
|---|---|---|---|---|
| TinyStories | 0.426 | 1.53 | 3.058 | 863,500 |
| Everyday Conversations | 0.872 | 2.39 | 3.113 | 54,430 |
| KB (diagnostic, not used for selection) | 2.966 | 19.42 | 3.128 | 15,508 |

**Final held-out test** (`python scripts/finalize.py`, run once at 2026-09-16T19:00:32, not forced; `final_eval.json` in the version directory):

| Held-out set | Loss (nats/char) | Perplexity | Unigram baseline loss | Characters scored | Mean similarity |
|---|---|---|---|---|---|
| TinyStories test (2,000 records) | 0.426 | 1.53 | 3.052 | 1,688,587 | — |
| Everyday Conversations official test (119) | 0.869 | 2.39 | 3.111 | 58,469 | — |
| KB final-test entries (8 unseen entries) | 3.191 | 24.31 | 3.125 | 19,088 | 0.217 |
| KB rephrasing diagnostic (32; **answer seen during training; wording held out**) | 0.025 | 1.03 | 3.150 | 5,749 | 0.677 |

- On TinyStories and Everyday, test loss matches validation (0.426 vs 0.426, 0.869 vs 0.872), far below the unigram baseline.
- On **unseen KB entries the model is slightly worse than the context-free unigram baseline** (3.191 vs 3.125): it has not learned facts that generalize.
- The rephrasing diagnostic's near-zero loss is teacher-forced (each next character is predicted given the true previous characters of an answer the model memorized in training). It shows memorization, not factual generalization or the ability to answer new questions. In generation, 32 greedy replies average 0.68 similarity to the reference. Many are verbatim, but some return a different memorized answer (for example, the Mars story for "What are the parts of a transformer block?").
- Final-test results were not used for any further tuning.

**What the samples show (greedy, in `validation.json` and `final_eval.json`; no quality score is implied):**
- Story prompts produce mostly grammatical TinyStories-style text that often drifts or repeats.
- Everyday chat replies start plausibly but lose coherence and can loop.
- KB validation questions (unseen answers) typically get a *memorized training answer* for a different question. For example, "Explain root mean square norm." returned the RoPE answer. This is memorization, not factual knowledge.
- Out-of-distribution questions get confident nonsense.

**Decoding speed** (measured with `stream_generate`, 300–400 new characters, batch 1):

| Device | Prompt | KV cache on | KV cache off (full recompute) |
|---|---|---|---|
| RTX 5090 | 649 chars | 491 chars/s | 444 chars/s |
| CPU (8 threads) | 649 chars | 555 chars/s | 36 chars/s |

On this GPU the cache gives little speedup because per-step kernel overhead dominates a model this small. On CPU it is about 15× faster. The chat tab always uses the cached path and reports measured tokens/s and time-to-first-token.

## Stage-2 conversation adaptation (attempted, rejected)

Goal: improve prompt relevance in chat by continuing training from the promoted checkpoint, not by retraining from scratch.

- **Prompt-format check first:** 3,099 live-format prompts were compared token for token with the stored training and validation windows. They covered every user turn with its history, for all three sources and both splits. All matched, and every supervised span ends with EOS. There was no serialization bug; `tests/test_data.py::test_live_chat_prompt_matches_training_serialization` guards this.
- **Run:** `python scripts/adapt.py --init 20260916-181935-run`
  - Initialized from `20260916-181935-run` weights (same architecture, tokenizer and context).
  - Mixture per epoch: Everyday train ×2, KB train ×4, and a fresh seeded subset of 3,000 TinyStories training windows. Expected target-character shares: Everyday 57%, TinyStories 37%, KB 6%.
  - Peak LR 3e-4 (5% warmup, cosine to 5%), batch 32, 5 epochs (1,340 steps). The training loop with per-epoch validation took 65 s (74 s including loading the checkpoint and the initial validation); the whole script, including the probe comparison, took about 2 minutes.
  - Selection used the same rule, `(TinyStories-val + Everyday-val) / 2`, with KB as a diagnostic only. Epoch 1 was saved; Everyday-val rose in later epochs.
- **Acceptance criteria** (written before the run; see `nanollama/compare.py`) and results:

  | Criterion | Before (`181935-run`) | After (`184538-adapt`, epoch 1) | Pass |
  |---|---|---|---|
  | Selection loss decreases by > 0.001 | 0.6486 | 0.6411 | yes |
  | Everyday-val decreases | 0.8716 | 0.8520 | yes |
  | TinyStories-val worsens by ≤ 0.02 | 0.4256 | 0.4302 | yes |
  | Looping probe replies do not increase | 2 / 26 | 2 / 26 | yes |
  | Fixed probes clearly more on-topic overall | — | — | **no** |
  | KB-val (diagnostic) | 2.966 | 3.037 | — |

  The fixed probes were 10 hand-written prompts plus 3 Everyday *validation* prompts, each run greedy and with seeded sampling, with the loop guard off. Greeting, identity, both dog-story prompts and the KB-style prompts were identical before and after. The picnic request turned into a verbatim, off-topic KB code answer; "What is Python?" and arithmetic stayed garbled; Everyday validation prompts were mixed, with one new loop.
- **Decision:** the small validation-loss gain did not produce visibly better relevance, so the adapted version was **not promoted**. `20260916-181935-run` stays active and not finalized. The rejected version is kept, never promoted, with `adaptation_comparison.json` and `adaptation_decision.json`.
- No test split was read while making this decision; `finalize.py` was run only afterwards, once, on the retained `20260916-181935-run`.
- `python scripts/promote.py <version>` verifies, probes and promotes any version explicitly.

## The app

| Tab | What it does |
|---|---|
| **Chat** | Streams real generations with persona/system prompt, temperature (≤ 0.15 = greedy; default 0), top-p, top-k, repetition penalty, max characters, seed, and an optional loop guard. Shows measured tokens/s, TTFT, count and total time. Includes presets (KB *training* queries, a free chat prompt and a story instruction, each labelled with its origin), reset, and a welcome note labelled as static text. |
| **Attention** | All layers × all heads for a BOS-prefixed prompt (≤ 64 characters). Grids use a sequential colour ramp; the masked future is hatched; hovering a cell shows its weight. |
| **Tokenizer** | Per-keystroke chips with ids, counts, characters per token, top-5 next-character probabilities, and the control-token table. |
| **Telemetry** | *Training & validation*: KPIs, loss chart (train, three validation sources, selection loss; hover tooltip plus table view), per-epoch validation, unigram baseline, mixture and windowing counts, samples. *Final held-out evaluation*: shown separately and only after `finalize.py`; otherwise "not finalized". No placeholder numbers. |
| **Architecture** | Block dataflow with dimensions read from the served checkpoint, formula cards for RoPE, SwiGLU, KV cache and RMSNorm, and a glossary. |
| **Retrain** | Epochs, batch size, LR and data budget (quick: seeded 12,000 story windows plus all chats and KB; full: all windows). Runs in a background thread with per-epoch progress; the old model keeps serving. The new version is verified, promoted, hot-loaded and marked not finalized. Server bounds: epochs 1–20, batch 4–64, LR 1e-4–1e-2. A quick 1-epoch retrain took 45 s on the RTX 5090. |

The server binds to `127.0.0.1` only and sets no cross-origin policy. Retraining replaces the
model for every client of this process.

### Canonical decoding defaults

One configuration, `DecodeSettings()` / `canonical_greedy()` in `nanollama/generate.py`, is the default everywhere:
- the chat API request defaults
- the UI controls, loaded from `GET /api/decoding-defaults`
- the fixed probes (`scripts/probe.py`, `scripts/adapt.py`)
- the generation samples written by `finalize.py` and `validation.json`

| temperature | top-p | top-k | repetition penalty | max new chars | loop guard | seed |
|---|---|---|---|---|---|---|
| **0 (greedy)** | 0.9 | 40 | **1.0 (off)** | 300 | **off** | none |

The default reply is therefore a direct model-decoding baseline with no heuristic applied. Top-p and top-k matter only when temperature is raised. The fixed-seed sampled probe uses the same settings with temperature 0.7 and seed 1234. Repetition penalty and the loop guard stay implemented, tested and adjustable, but never silently change the default.

This replaced an earlier inconsistency: the chat defaulted to temperature 0.7 with repetition penalty 1.1, while probes used 1.0, so "greedy" output differed between the UI and the evaluation. Regression tests check that the API, served HTML and probe/final-evaluation defaults are identical, and that the live chat stream reproduces the probe script's reply for the same prompt, history, system prompt and settings. A manual check through the running server matched on all 26 probe runs.

### Loop guard: off by default (intentional change from the source)

The source enabled two anti-loop rules by default: no third identical character in a row,
and a repeated-trigram breaker. Both are implemented and tested, but here they are an
**optional toggle, off by default**, because they measurably corrupt ordinary English from
the trained model. They block legitimate repeats such as "the"; with the guard on, a probe
story read "went to thd the sun witch winkers". They never affect loss or perplexity.
Evaluation samples use the canonical defaults (guard off); `validation.json` also records
guard-on replies for the fixed probes as a side-by-side diagnostic.

## Other intentional corrections to the source behaviour

- No retrieval-first chat, prompt snapping or artificial per-character delay. Reported throughput is real.
- The repetition penalty is applied: CTRL-style over the last 32 generated characters.
- The KV cache is used on the served path.
- The validation split is disjoint from training (the source leaked duplicates across its split). Final test sets are separate and scored only by `finalize.py`.
- The telemetry, tokenizer, attention and retrain features share one consistent contract. The attention view returns every layer and head.
- The architecture view reads the live checkpoint config instead of stale numbers.
- Retraining is non-blocking, validated and versioned.

## Limitations

- A 4.8M-parameter character model trained for ~23 minutes: it is **not** factually reliable, does not follow instructions robustly, and invents content. Out-of-distribution questions get nonsense.
- KB answers are memorized for training entries and do not generalize to unseen entries (see the KB diagnostic loss). Unrelated prompts often trigger a verbatim KB answer instead. For example, "Tell me a short story about a dog." returns the memorized rainy-day story, and "Can you help me plan a picnic?" starts with the palindrome answer's first line and degrades into garbled code.
- Only six system prompts were trained; custom system prompts are out of distribution.
- Validation numbers guided checkpoint selection and the mixture/selection-rule change; only `finalize.py` results estimate held-out performance.
- The TinyStories sample (60k of 2.48M records) and the 8-epoch budget are practicality choices for this machine, not tuned optima.
