# Customer Segmentation & Clustering Intelligence Platform

An unsupervised customer-segmentation platform built on the real
[Customer Personality Analysis](https://www.kaggle.com/datasets/imakash3011/customer-personality-analysis)
retail dataset. It derives eight behavioural attributes and four engineered interaction features,
runs a tournament of five clustering families on shared internal-validity metrics, trains and serves
a production K-Means model, profiles the discovered clusters into named marketing personas, projects
customers into 2D with PCA and t-SNE, classifies new customers in real time, and runs an autonomous
four-phase hill-climbing search over features and hyperparameters — all behind a two-view Streamlit
dashboard.

> **Reproduction note.** This is an independent reimplementation from a written specification of an
> existing project. Where that specification documented defects — personas bound to arbitrary cluster
> indices, a retrain control that did nothing, hardcoded metrics presented as measurements, a
> consensus-ensembling phase that was never computed — this implementation does the intended thing
> instead and says so. See [Deviations from the source](#deviations-from-the-source-specification).

---

## Quick start

```bash
conda activate cmpe255
pip install -r requirements.txt

python -m segmentation.data --download      # fetch + clean the dataset  (~5s)
python -m segmentation.pipeline             # fit, evaluate, export artifacts (~4s)
python -m segmentation.autoresearch         # run the hill-climbing search (~20s)

pytest -q                                   # 136 tests, offline, ~2 min
streamlit run app/main.py                   # open the dashboard
```

A committed `.streamlit/config.toml` opts out of Streamlit usage telemetry and runs the server
headless, so the first launch on a clean machine never stops to ask for an email address. Because
headless mode does not open a browser tab automatically, open the printed `Local URL` yourself.

The dashboard also runs both the pipeline and the search on demand, so the two intermediate commands
are optional once the data is downloaded — but running them first gives you a populated dashboard on
first load.

## The data

| | |
|---|---|
| **Source** | [Customer Personality Analysis](https://www.kaggle.com/datasets/imakash3011/customer-personality-analysis) (`imakash3011`), public, no credentials required |
| **Raw** | 2,240 customers × 29 columns, tab-separated |
| **After cleaning** | **2,197 customers** (43 dropped) × 8 behavioural attributes |
| **Location** | `data/raw/` and `data/processed/` — both gitignored, regenerated by script |

Nothing is committed: `python -m segmentation.data --download` fetches and prepares everything. If
the download endpoint ever changes, the script fails with manual-download instructions rather than
proceeding silently.

### Cleaning rules

All four are deliberate and are reported in the dashboard's CRISP-DM panel:

* **Missing income → dropped** (24 rows, ~1%). Imputing a household income would invent the single
  strongest clustering signal.
* **Income above the 99.5th percentile → dropped**, which clears the `666666` data-entry artefact.
* **Age outside 18–90 → dropped**, which clears the 1893 and 1899 birth years.
* **No purchase history → dropped**, because a discount share and a conversion rate are both
  undefined for a customer who never purchased.

### The eight behavioural attributes

| Attribute | Derivation |
|---|---|
| `age` | `2014 − Year_Birth` (2014 is the dataset's enrolment-year reference) |
| `income_k` | `Income / 1000` |
| `spending_score` | **Derived** 1–100 purchase-engagement score — see below |
| `recency_days` | `Recency` |
| `total_spend` | `sum(Mnt*)` across all six product categories over the two-year history |
| `web_visits_month` | `NumWebVisitsMonth` |
| `discount_sensitivity` | `NumDealsPurchases / (Web + Catalog + Store purchases)`, clipped to [0, 1] |
| `household_size` | `1 + partnered + Kidhome + Teenhome` |

**Two derivations deserve explanation.**

*Spending score.* The raw dataset has no spending score, so one is constructed. The obvious choice —
a percentile rank of `total_spend` — measures **ρ = 0.91** (Spearman) against `total_spend` itself,
which would hand the clustering two near-duplicate monetary dimensions. Purchase-frequency variants
are no better (ρ = 0.89–0.93; frequency and spend are intrinsically coupled in this data). The score
is therefore built from two *non-monetary* behavioural signals, equally weighted:

```
spending_score = 1..100 rank of
    0.5 · pct_rank(channel purchases / (web visits + 1))   # conversion efficiency
  + 0.5 · pct_rank(AcceptedCmp1..5 + Response)             # campaign responsiveness
```

This is the semantic analogue of a retailer-assigned engagement score, and measures **ρ = 0.860**
against `total_spend` on the cleaned data — correlated, as any genuine purchase-behaviour signal must
be, but no longer a duplicate of the monetary axis. A regression test pins this correlation below
0.90 so the problem cannot silently return.

*Discount sensitivity.* `NumDealsPurchases` counts purchases made *with a discount*, while the three
`Num*Purchases` columns partition purchases *by channel* — a discounted purchase is still made
through some channel. Verified empirically: `NumDealsPurchases ≤ Web + Catalog + Store` holds for
2,237 of the 2,240 raw rows. The denominator is therefore the channel counts only; adding deals in
would double-count them and systematically understate the ratio.

### Engineered features

Four interaction features are appended, giving the 12-column matrix used for all clustering and
inference. The `+1` denominators are deliberate divide-by-zero guards.

| Feature | Formula |
|---|---|
| Discretionary ratio | `income_k / (spending_score + 1)` |
| Monetary velocity | `total_spend / (recency_days + 1)` |
| Digital engagement | `web_visits_month × (spending_score / 100)` |
| Deal affinity | `discount_sensitivity × (1 − spending_score / 100)` |

All 12 columns are z-score standardized. **The fitted scaler is persisted with the model and the
ordered column list and is only ever applied at inference** — re-fitting a scaler on a single record
would silently destroy every prediction. A test asserts that a training customer resubmitted through
the inference path lands in the cluster the model assigned it.

## Results

Every number below was produced by this pipeline at seed 42 and can be regenerated with
`python -m segmentation.pipeline`. They are measurements, not targets.

### Algorithm leaderboard

All five families, the production model and the elbow sweep are fit and scored on the **same**
2,197-customer standardized matrix, which is what makes their metrics comparable.

| Algorithm | Family | Silhouette | Davies–Bouldin | Calinski–Harabasz | Clusters |
|---|---|---:|---:|---:|---:|
| **K-Means** *(served)* | Centroid partitioning | **0.2172** | 1.3579 | 575.6 | 5 |
| Spectral | Graph / spectral | 0.2085 | 1.2967 | 545.6 | 5 |
| Agglomerative | Hierarchical (Ward) | 0.1864 | 1.3815 | 488.1 | 5 |
| Gaussian mixture | Probabilistic mixture | 0.1029 | 2.0903 | 413.3 | 5 |
| DBSCAN | Density-based | — | — | — | 1 *(degenerate)* |

**DBSCAN's ε is chosen by the k-distance knee heuristic**, a purely geometric property of the data
that never consults silhouette. Tuning it on the ranking metric would give DBSCAN an optimisation
advantage no other entrant receives. On this data the rule yields ε = 2.342, which collapses
the partition to a single cluster — reported as **degenerate with undefined metrics**, rather than
given a placeholder score that would let a failed run take a rank. This dataset simply has no
density-separated structure at that scale.

### Choice of k

| k | 2 | 3 | 4 | **5** | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|---|
| Silhouette | **0.2926** | 0.1999 | 0.2108 | 0.2172 | 0.1891 | 0.1799 | 0.1803 | 0.1665 |

**The two standard criteria disagree.** The inertia knee — the elbow method — falls at **k=5**, the
served cluster count. Silhouette peaks at **k=2**, which splits the base 1130/1067 into "affluent and
engaged" versus "price-led": real structure, but too coarse to support differentiated marketing.

Silhouette is biased toward small k (merging groups raises mean inter-cluster distance), so its
preference for the coarsest split is weak evidence on its own. So k=5 is supported by one of the two
criteria and by the business need for actionable personas — it is neither proven by the data nor
asserted against it. Both computed values are shown wherever k is discussed, from a single shared
helper (`elbow.verdict`) so every surface tells the same story from the same numbers.

Real behavioural data of this kind yields modest silhouettes: customer behaviour is continuous, not
naturally clumped into well-separated balls. Nothing was tuned to inflate these figures.

### Discovered personas

Persona identity is matched to cluster **content**, never to the arbitrary K-Means label index.

| Cluster | Persona | Size | Income | Spending score | 2-yr spend | Recency | Fit |
|---|---|---:|---:|---:|---:|---:|---:|
| 0 | 👑 VIP Champions | 541 (24.6%) | $75.4k | 81 | $1,297 | 52d | 89% |
| 1 | 🏷️ Bargain Hunters | 836 (38.1%) | $33.9k | 25 | $123 | 50d | 88% |
| 2 | 🧭 Mainstream Loyalists | 681 (31.0%) | $56.3k | 62 | $713 | 48d | 92% |
| 3 | 🪟 Window Shoppers | 104 (4.7%) | $33.6k | 3 | $25 | 51d | 89% |
| 4 | ⚡ Recent Big Spenders | 35 (1.6%) | $69.4k | 74 | $1,189 | **1d** | 93% |

**How a persona is chosen.** Each cluster is placed at its **percentile** within the whole customer
base on eight attributes, so 0.5 is the median customer on every axis. Each persona in a
twelve-entry catalogue has a narrative that makes explicit claims — "higher income", "low spend",
"mid-sized baskets" — and every claim is recorded as a *signature* the cluster must satisfy:

* "high" means the cluster sits at or above the 60th percentile,
* "low" at or below the 40th,
* "average" between the 35th and 65th.

A persona is only ever shown on a cluster that satisfies **every** claim its narrative makes. Among
the personas that pass, the one with the closest overall profile is chosen (a one-to-one Hungarian
assignment, with contradicting pairs excluded). If no persona passes, the cluster is shown as a
numbered segment described from its own data — e.g. *"Segment 6 · Discount-driven, large households,
lower income"* — rather than given a marketing narrative its numbers contradict. At k=5 all five
segments carry a persona; at higher k some segments legitimately fit none.

**Why it is built this way.** A final user-facing audit inspected every assignment for k=2 through 10
by hand and found that simpler schemes produce plausible-looking but wrong labels:

* Matching on an averaged distance let several agreeing attributes outvote the one a persona is
  named for — a "Lapsing Browsers" label (*"last purchase far behind them"*) landed on a cluster with
  below-average recency.
* Recency and household size were not matched on at all, so narratives claiming them went
  unchecked. The 35-customer cluster above bought **yesterday**, yet was labelled "Premium
  Occasionals — infrequent shoppers".
* A linear rescaling of attributes put the median customer's spend at 0.21 instead of 0.5, so a
  cluster at the 78th percentile of spend read as "mid-sized baskets".

Tests now pin the invariant directly: for every served persona, every narrative claim holds for its
cluster's data.

### Projections

PCA (2 components) captures **55.5%** of total variance and is persisted, because it is reused at
inference to place a newly classified customer on the same canvas. t-SNE (perplexity 30) is fitted on
a deterministic 1,200-customer sample and is **not** persisted — it has no out-of-sample transform,
which is precisely why the live-prediction marker appears in PCA mode only.

### AutoResearch

A four-phase greedy hill climb on a 1,600-customer sample, starting from the eight raw attributes:

```
Start  0.18417  (K-Means, best backbone family on raw attributes)
Best   0.22899  (+24.3% vs its own starting score)
13 steps · 6 accepted · 6 rejected
```

All six candidate features were accepted; every hyperparameter trial and the consensus ensemble were
rejected. Three properties are worth calling out:

* **The acceptance gate is real and has two conditions.** A candidate must improve silhouette by more
  than +0.0005 *and* leave every cluster holding at least 1% of customers. The second condition
  exists because silhouette alone is gameable: in this very run, agglomerative average linkage scored
  **0.4536** — nominally the best figure seen — by splitting the base 1580/11/7/1/1. That is a
  segmentation of nothing. It is rejected, and the step's reflection explains why. The constraint is
  applied identically to every candidate in every phase.
* **The search is stateful.** An accepted feature mutates the working matrix for all later steps, so
  the trajectory is order-dependent and phases 3 and 4 are evaluated against an evolved feature set.
* **Phase 4 actually computes the consensus.** The co-association matrix is built from the K-Means
  and Gaussian-mixture partitions, the consensus is extracted by average-linkage clustering over
  `1 − co-association`, and the resulting silhouette and the **measured** 81.5% pair co-assignment
  rate are both computed from the data. It is then rejected on its merits at Δ −0.003.

**The +24.3% is measured against this run's own phase-1 starting score.** It is not a gain over any
external benchmark and it does not describe the deployed model. AutoResearch findings are exploratory
and are deliberately not auto-promoted into production, so that persona identities stay stable and
the served metrics describe exactly the model being served. Its silhouette is measured on a
different sample and feature set, so it is **not comparable** to the served model's 0.2172; the
dashboard labels it as a separate search wherever it appears.

### External reference points

Published third-party results exist on this dataset (silhouette ≈ 0.62 at k=2; ≈ 0.54 at k=4), but
each uses a different feature subset, different cleaning and outlier rules, a different k, and in one
case measures silhouette in a PCA-reduced space rather than the modelling space. **Silhouette is not
transferable across feature spaces**, so these figures are shown as a cited contextual panel
*outside* the ranked leaderboard — never sorted, ranked or badged against the models trained here.
Nothing on that panel is computed by this project. Sources are linked in the dashboard.

## Using the dashboard

**Segment explorer** — problem framing with live figures; five persona cards that cross-filter the
manifold; a PCA/t-SNE scatter with per-customer hover detail; and a live classifier with a slider for
**all eight** attributes (the source left two of them unreachable), which returns a persona,
a proximity score, the centroid distance and a marker on the PCA canvas.

**Admin console** — three tabs:

* *Benchmarks* — KPI tiles, a plain-language glossary explaining every metric on screen (silhouette,
  Davies–Bouldin, Calinski–Harabasz, inertia/WCSS, noise) for readers without a clustering
  background, the leaderboard with degeneracy handling, the auditable DBSCAN ε rule with its
  k-distance plot, the k-sweep panels, and the external reference panel.
* *AutoResearch* — the backbone tournament grid, outcome tiles, the optimisation trajectory, a
  filterable experiment stream (by phase and decision), a per-step inspection modal showing the exact
  transformation, the resulting partition shape, the reflection and the active hyperparameters, plus
  JSON export of the full run record and an on-demand relaunch.
* *Radar profiles* — six normalized axes with per-persona isolation and a breakdown list.

**Methodology** opens the six-phase CRISP-DM report. Every figure in it is read from the artifacts
this pipeline produced, so it changes when you retrain.

**Retrain** opens the studio. Cluster count (2–10), training-sample size and seed **all reach the
pipeline and all change the result** — the source's k control was validated and then ignored.

The confidence percentage shown with a prediction is a **normalized inverse-distance proximity
score, not a probability**. With k centroids it can never fall below 1/k. The UI says so.

## Project layout

```
segmentation/          data-science core — no UI-framework imports anywhere
  config.py            constants, paths, persona archetypes, validation ranges
  data.py              download, clean, derive the eight attributes
  features.py          engineered features + the persisted-scaler contract
  tournament.py        five families, validity metrics, the DBSCAN ε rule
  model.py             production fit / persist / load
  projections.py       PCA (persisted) + t-SNE (not persisted)
  personas.py          content-based archetype matching
  elbow.py             k sweep, empirical peak and knee
  inference.py         validation, classification, proximity score
  autoresearch.py      four-phase hill climb
  pipeline.py          orchestration + retraining
  engine.py            artifact loading and version stamping
app/
  state.py             the only Streamlit caching in the project
  main.py              shell, navigation, modals, retraining studio
  explorer.py          segment explorer
  admin.py             benchmarks, AutoResearch, radar
  crispdm.py           CRISP-DM report, populated from live artifacts
.streamlit/            committed config: telemetry off, headless, no first-run email prompt
tests/                 136 offline tests against a 240-row committed fixture
artifacts/             regenerable outputs (gitignored)
data/                  raw + processed data (gitignored)
```

The core package is deliberately framework-independent: two tests assert that no module imports
Streamlit and that the whole package imports with Streamlit blocked. All caching lives in
`app/state.py`, which wraps the plain-Python engine in `@st.cache_resource` keyed on an artifact
version stamp — so a retrain is picked up by every session without a restart.

## Testing

```bash
pytest -q          # 136 tests, ~2 min, fully offline
```

Tests run against a committed 240-row fixture in the raw schema that deliberately includes every
edge case the cleaning rules exist for (a null income, the 666,666 outlier, an 1893 birth year, a
customer with no purchase history, a deals-exceed-channels row, a junk marital status, a zero-visit
customer). No test downloads data or runs a full-scale fit. Artifact paths are redirected to a temp
directory, so tests never touch your real artifacts.

Coverage is focused on where the scientific risk actually is: attribute derivation and cleaning
rules, the engineered-feature formulas and their divide-by-zero guards, the persisted-scaler contract
and column-order coupling, degenerate-partition and noise handling in the metrics, the DBSCAN ε rule
being a pure function of the data, persona assignment following content rather than label index
(including invariance under label permutation), every served persona's narrative claims holding for
its cluster on a true percentile scale, the data-derived fallback for segments no persona fits,
input validation, inference determinism and
agreement with training assignments, the AutoResearch gate in both its conditions, search
statefulness, the consensus phase computing a real co-assignment rate, artifact round-trips,
retraining changing what is served, framework independence, the live-prediction marker staying in
step with the result card, every CRISP-DM report phase rendering from live artifacts and from an
empty artifact set, and an application smoke test over every view including the empty state.

## Deviations from the source specification

**User-approved adaptation.** The source generated its data synthetically while presenting it as the
Kaggle Customer Personality dataset. At the user's direction this implementation uses that **real**
dataset instead. Consequences, all deliberate:

* There are no ground-truth group labels, so the project is genuinely unsupervised end to end and no
  external agreement measure is reported anywhere.
* The source's 3,500-row evaluation subset existed only to make exact metrics affordable on 10,000
  synthetic rows. At 2,197 customers exact metrics are cheap, so **the shared evaluation set is the
  full cleaned dataset** — and the production model is now fit on that same matrix, making the
  comparison stricter than the source's (which scored a full-data fit against subset-fitted
  entrants).
* The retrain studio's "dataset size" control becomes **training-sample size** (500 … 2,197, drawn
  deterministically from the seed), the closest meaningful analogue for a fixed real dataset.
* The 1,200-customer t-SNE/scatter sample, the k=2..9 sweep, the +0.0005 gate, perplexity 30, the
  1e-5 inference guard and seed 42 are all unchanged.

**Documented source defects, implemented as intended rather than reproduced:**

| Source defect | What this implementation does |
|---|---|
| Personas bound positionally to K-Means label indices, producing visibly wrong labels | Personas matched to cluster **content**; every narrative claim verified against the cluster's percentiles; segments no persona fits described from their own data |
| Retrain cluster count validated then ignored | k reaches the pipeline and changes everything downstream |
| k=5 hard-asserted as elbow and silhouette peak | Both computed; disagreement with the served k stated plainly |
| Consensus ensembling logged as accepted with a fabricated ">91.4%" figure | Co-association consensus genuinely computed, measured and scored — and rejected on its merits |
| Two classifier inputs with no UI control | All eight attributes have controls |
| "Champion" badge landing on the static reference row | Reference sits outside the ranking; leader and served badges are separate |
| "+21% gain" conflating two different baselines | Improvement labelled as relative to the search's own starting score, everywhere it appears |
| Hardcoded metrics in the banner, KPI tiles and CRISP-DM report | Every figure read from live artifacts; empty states degrade to guidance |
| Degenerate runs scored as silhouette 0 / DB 99 | Reported as undefined and sorted last |

**Not implemented**, because the specification classified them as documented-but-unimplemented source
intent rather than requirements: a printable/exportable CRISP-DM report, distance-metric and
PCA-pre-reduction search inside AutoResearch, and additional linkage/covariance variants in the
search space.

## Environment

Python 3.11 in the `cmpe255` conda environment. Dependencies are in `requirements.txt`
(scikit-learn, pandas, numpy, scipy, joblib, pyarrow, streamlit, plotly, pytest). A full pipeline run
takes about 4 seconds and an AutoResearch run about 20 seconds on CPU, so retraining from the
dashboard is interactive.
